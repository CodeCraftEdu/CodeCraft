# Textes élèves

Ces règles s’appliquent à tous les modules et parcours, y compris aux démonstrations et à leurs explications.

- Donner l’action attendue, l’observation à faire et l’explication utile à la notion travaillée.
- Préférer une consigne positive et concrète à « ne fais pas ceci ». Garder une interdiction seulement si elle évite un risque ou une confusion réelle dans l’exercice.
- Décrire le chemin principal. Ne pas empiler les scénarios de connexion, d’installation, de matériel absent ou d’aide à la manipulation dans chaque introduction. Placer un dépannage indispensable à l’endroit où le problème survient.
- Garder les précautions de sécurité, de confidentialité et de sauvegarde, ainsi que les distinctions techniques nécessaires (par exemple title et h1, ou une simulation et du matériel réel).
- Réserver aux guides professeur les remarques sur les acquis, la validation, les aides reçues et les limites d’évaluation. Le texte élève doit expliquer ce qu’il va apprendre ou faire.
- Éviter les listes de fonctionnalités non requises : indiquer simplement les éléments attendus. Marquer une activité facultative une seule fois.
- Dans un comparateur, faire correspondre le code, le résultat et l’explication. Un libellé court comme « Onglet simulé » suffit à identifier une représentation.
- Pour un aperçu d’image, afficher une vraie balise `<img>` : l’image chargée ou le rendu du navigateur quand le fichier est absent. Garder les explications hors de l’aperçu, sans remplacer l’image par un encart descriptif.
- Sauf demande explicite, ne pas ajouter de disclaimer sur le fonctionnement ou les limites des aperçus : ni rappel du vrai onglet, ni explication de ce que la démonstration ne fait pas, ni rappel générique de tester dans son fichier. Garder l’explication de la notion et le résultat à observer. Les précautions de sécurité, de confidentialité et de sauvegarde restent distinctes de ces disclaimers.
- Sous les démonstrations interactives, garder uniquement l’explication du résultat observé. Ne pas ajouter de sous-description grise, de note secondaire ou de rappel générique après cette explication, sauf demande explicite. Le rendu commun ne doit pas afficher automatiquement le champ `note` des anciennes démonstrations.
- Utiliser des titres courts, sans numérotation décorative. Aucun tiret long dans les textes du site, y compris les titres, légendes, boutons, guides professeur et noms d’onglet. Utiliser une phrase, une virgule, deux-points ou des parenthèses ; pour un intervalle, écrire « de … à … » ou utiliser le tiret court.
- Afficher les consignes, listes à cocher, aides et actions sans numérotation automatique. Leur ordre visuel suffit ; conserver seulement les nombres qui font partie de la notion, du code ou de la structure du parcours.
- Dans le texte courant, écrire les balises avec leurs chevrons (`<html>`, `<body>`). Encadrer les attributs, propriétés CSS et expressions de code avec des accents graves pour obtenir le style de code en ligne, par exemple `lang="fr"`, `display: flex` ou `print()`. Réserver ce traitement aux éléments de code, pas au vocabulaire courant ni aux titres. Les blocs de code restent inchangés.
- Les blocs de code utilisent un rendu éditeur commun : fond sombre neutre, balises roses, attributs vert clair, chaînes jaunes, commentaires verts et repères de ligne discrets. Les numéros de ligne servent au repérage du code, contrairement à la numérotation décorative des consignes. Conserver exactement le texte et les espaces du code, sans inclure les numéros dans la copie. Le code en ligne reste sobre.
- Tous les exemples et indices de code partagent un cadre avec un en-tête de fichier, des coins biseautés et un liseré inférieur teinté du parcours. Employer le nom réel du fichier lorsqu’il est connu ; sinon, utiliser un nom de référence adapté au langage (`index.html`, `style.css`, `script.js`, `main.py`) ou « Code » pour les extraits non identifiés.
- Pour les premières images HTML, travailler avec une adresse d’image en ligne et un chemin relatif accompagné de l’arborescence du projet. Fournir des fichiers PNG ou JPEG ; garder les sources encodées et le code SVG hors de ces activités.

Le rendu prend aussi en charge les anciens noms de balises et d’attributs seuls (src, alt, href, etc.) en texte brut dans les modules Web, y compris dans les consignes, indices, critères et retours des démonstrations, sans modifier les données ni ajouter des chevrons aux sélecteurs CSS. Les mots ambigus comme « a », « article » et « style » nécessitent une mention explicite de balise/attribut ou le balisage par accents graves. Les noms de fichiers et les textes des autres univers restent inchangés.

Avant de livrer un texte, relire chaque précaution : sert-elle l’action, la compréhension ou la protection de l’élève ici ? Sinon, la retirer. Ne pas supprimer automatiquement toutes les phrases négatives : certaines expliquent une différence essentielle ou un diagnostic.
